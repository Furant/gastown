# Project-owned execution node selection

Projects own the selection of execution nodes. A node represents a machine and its installed tool capabilities, identity, owner and sharing scope; users never choose projects in node registration or editing. Remote projects may select zero or several nodes. Zero nodes is valid while setting up, but task execution requires a selected usable node. Multiple projects may select the same node. Private local Git projects retain exactly their owner-selected paired node and cannot silently move to another machine.

`projects.node_ids` is the source of truth, exposed as `nodeIds`. `PATCH /projects/:id` changes the remote project selection for its owner or authorized administrator; selected nodes must be usable by both actor and project owner. Node create/edit no longer accepts nonempty `projectIds`. Node details may show associated projects as derived read-only information. Existing node tokens, capability reports and local pairing identities remain intact.

A one-time transactional migration reverses legacy node project grants into project node selections, restricted to the same organization; local projects derive their selection from `local_node_id`. Record migration completion so clearing a project selection is preserved across restarts. The legacy column is no longer consulted for authorization. Preserve existing task/output data and local node config files.

Task creation, polling, transfers, quota failover, checkpoint delivery, configuration manifests and permission revocation must all consult the project selection. Node sharing and tool-connection sharing remain permission checks. Connection project grants remain independent because they authorize use of the owner's tool account; they do not configure the machine/project relation. Removing a selected node requests stop for affected active jobs, cancels affected queued jobs, and retains completed/awaiting-review outputs. An in-flight handoff also depends on its pending target node: removing that target converts the source stop to cancellation, so the final stop acknowledgment cannot strand a transfer. Reject unselected handoff targets before asking the source to stop. A source still requires authenticated stop acknowledgment before any subsequent writer starts.

The project page is the only place to configure the relationship. Remote project creation includes node selection; each remote project card offers an execution-node editor. Local project selection stays in the existing paired-node field. Node forms contain machine identity/sharing only. After selecting a node, users synchronize repository mappings on that machine and restart its worker as before. The console never opens a remote/local repository path itself.

Validation covers legacy migration and restart idempotence, standalone node registration, project selection/editing, cross-user/org denial, local-device restrictions, node token stability, task revocation, worker config manifests, and a real fixture CLI task on a second project selecting the existing node. Browser checks verify empty node forms, project-owned multi-selection and persisted editing. Use isolated fixtures, with no real provider calls or changes to user repositories.
